# API contract

> **Status:** Implemented so far: the error envelope and status-code policy of §2, the pagination shape
> of §3, all four authentication endpoints in §4, the **Users** section of §5 including the staff
> directory, and the operational endpoints in §5 (`/healthz` and `/readyz`, each mounted versioned and
> unversioned). People, cases, documents, dashboard and audit endpoints are still planned. It is the
> contract each phase must honour; it is updated as endpoints land, and the OpenAPI document generated
> by FastAPI is the machine-readable source of truth for what is actually served.
>
> There is no login *UI*: Phase 2 delivered the authentication backend, and the browser screens are
> Phase 3.
> Last reviewed: 2026-09-06

## 1. Conventions

- Base path `/api/v1`. The version is in the path; breaking changes create `/api/v2` rather than
  mutating `v1`.
- JSON in and out, UTF-8, `application/json`; the only exception is submission upload
  (`multipart/form-data`) and download (binary stream).
- Resources are addressed by UUID. `internal_case_number` is a searchable business key, never a path
  identifier, so renumbering or formatting changes can never break links.
- Timestamps are UTC ISO-8601 with offset (`2026-09-01T09:12:33Z`). Business dates are `YYYY-MM-DD`
  with no time and no timezone.
- Field names are `snake_case` (matching the database and Pydantic); the web client's generated types
  follow suit, so there is no renaming layer to drift.
- Enum values are the English `SCREAMING_SNAKE_CASE` codes from
  [`domain-model.md`](domain-model.md). The API never returns Hebrew display labels; the web app owns
  all Hebrew copy (ADR-0014).
- Responses are always typed Pydantic models. ORM objects are never serialised directly, so adding a
  column cannot accidentally publish it.
- All mutating requests require the session cookie **and** the `X-CSRF-Token` header.

## 2. Error envelope

Every non-2xx response, including validation failures, uses one shape:

```json
{
  "error": {
    "code": "CASE_INVALID_STATUS_TRANSITION",
    "message": "Cannot move a case from CLOSED to OPINION_IN_PROGRESS.",
    "details": [
      { "field": "to_status", "issue": "not_allowed_from_current_status" }
    ],
    "request_id": "01J9Z3K7QF8V2M4S6T8W0Y2A4C"
  }
}
```

- `code` is stable and machine-readable; the web app maps it to Hebrew text.
- `message` is English, for developers and logs. It never contains stack traces, SQL, or internal
  identifiers beyond what the caller already supplied.
- `details` is always present and always a list — empty when there is nothing per-field to say — so a
  client can iterate it without a null check. Each entry is `{"field", "issue"}`, naming the field and
  a machine-readable problem, never the rejected value (see [`security.md`](security.md) §5).
- `request_id` matches the server log entry, which is how support questions get answered without
  leaking internals. It is also returned as the `X-Request-ID` response header on every response,
  successful or not, and is generated by the server: an `X-Request-ID` sent by a client is ignored.

The envelope is produced by handlers registered on the application, so it covers routes that do not
exist (`404`), methods that are not allowed (`405`), validation failures raised by FastAPI (`422`) and
unhandled exceptions (`500`) — not only errors the application raises deliberately. Infrastructure
codes in use today: `BAD_REQUEST`, `VALIDATION_ERROR`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `CONFLICT`,
`TOO_MANY_REQUESTS`, `SERVICE_UNAVAILABLE`, `INTERNAL_ERROR`. Domain-specific codes such as
`CASE_INVALID_STATUS_TRANSITION` arrive with the features that raise them.

Authentication, authorization and user-administration codes, all in use today:

| Code | Status | Meaning |
| --- | --- | --- |
| `AUTH_REQUIRED` | `401` | No session cookie, or it matches no usable session |
| `AUTH_INVALID_CREDENTIALS` | `401` | Login failed. The *only* login failure, whatever the cause |
| `AUTH_SESSION_EXPIRED` | `401` | The session was revoked, hit its absolute cap, or went idle too long |
| `AUTH_ACCOUNT_INACTIVE` | `401` | The session resolved but the account has been deactivated |
| `CSRF_TOKEN_INVALID` | `403` | Missing or non-matching `X-CSRF-Token` on an unsafe method |
| `PASSWORD_CHANGE_REQUIRED` | `403` | A temporary password must be rotated first (ADR-0026) |
| `FORBIDDEN` | `403` | Authenticated, endpoint visible, role not permitted |
| `PASSWORD_INVALID` | `422` | The proposed password fails the policy; `details` carry the reasons |
| `CURRENT_PASSWORD_INVALID` | `422` | The `current_password` supplied to a self-service change is wrong |
| `USER_NOT_FOUND` | `404` | No such user |
| `USER_EMAIL_CONFLICT` | `409` | That address already belongs to an account |
| `USER_SELF_DEACTIVATION` | `409` | An admin may not deactivate themselves |
| `USER_LAST_ADMIN` | `409` | The last active admin may not be deactivated or demoted |

`AUTH_SESSION_EXPIRED` and `AUTH_ACCOUNT_INACTIVE` are distinguishable from `AUTH_REQUIRED` on
purpose: the caller has already proved who they are, so telling them why they were logged out is
useful rather than a disclosure. Login is the opposite case, and gets exactly one code.

### Status code policy

| Code | Used for |
| --- | --- |
| `200` | Successful read or update returning a body |
| `201` | Resource created (with the created resource as the body) |
| `204` | Successful action with no body (login, logout, soft removal) |
| `400` | Malformed request that is not a field-level validation problem |
| `401` | Missing, expired or revoked session (`AUTH_REQUIRED`), or failed login (`AUTH_INVALID_CREDENTIALS`) |
| `403` | Authenticated, resource visible, action not permitted for this role; also CSRF failure |
| `404` | Resource does not exist **or** is outside the actor's visibility scope (ADR-0021) |
| `409` | State conflict: duplicate business key, invalid status transition, optimistic-concurrency version mismatch |
| `413` | Upload exceeds the configured size limit |
| `415` | Upload type not in the allowlist |
| `422` | Field-level validation failure |
| `429` | Rate limit / login throttling |
| `500` | Unexpected server error; generic message plus `request_id` only |

## 3. Pagination, filtering and sorting

List endpoints accept `page` (1-based) and `page_size` (default 25, maximum 100) and return:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 25
}
```

Offset pagination is chosen deliberately: the dashboard needs total counts and page numbers, and the
data volume for a single consultancy makes keyset pagination premature (ADR-0016). Sorting uses
`sort` with a validated enum value and `order` (`asc`/`desc`); arbitrary column names are never
accepted. Repeatable filters use repeated query parameters (`?status=NEW&status=DOCUMENTS_REVIEW`).

## 4. Authentication endpoints

All four are **implemented**.

| Method | Path | Access | Notes |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/login` | public | Body `{email, password}`. `204` + session and CSRF cookies. Uniform `401` on any failure; throttled per IP (`429`) |
| `POST` | `/api/v1/auth/logout` | authenticated | Revokes the current session, clears cookies. `204` |
| `GET` | `/api/v1/auth/me` | authenticated | `{id, email, full_name, role, must_change_password}` |
| `POST` | `/api/v1/auth/password` | authenticated | Body `{current_password, new_password}`; rotates the session |

Exact behaviour of the four, since the details are load-bearing:

- **login** — the email is trimmed and lower-cased before lookup; the password is never trimmed,
  because whitespace is a legitimate part of a passphrase. A success issues a new session row and
  sets both cookies; nothing is returned in the body, because the session *is* the result. Logging in
  again does not disturb an existing session — two browsers are two sessions. Any failure is
  `401 AUTH_INVALID_CREDENTIALS` and sets no cookie. CSRF is not required: there is no session to bind
  a token to yet.
- **logout** — authenticated and CSRF-protected. Revokes *this* session only (other browsers stay
  logged in), clears both cookies with the attributes they were set with, and returns `204`. The
  cookie clearing is tidy-up: the row is revoked server-side, so the old cookie is already useless.
- **me** — the five safe fields above and nothing else. No session id, no token, no hash, no lockout
  state. It is one of the three endpoints permitted while `must_change_password` is true, which is how
  a client discovers that it must send the user to a password-change screen.
- **password** — authenticated and CSRF-protected. Verifies `current_password`, validates the new one
  against the policy (including "not the same as the current one"), replaces the hash, clears
  `must_change_password` and any lockout counters, **revokes every existing session**, then issues a
  fresh one and sets both cookies. All of it in one transaction. The caller therefore stays logged in
  on a new session while every other browser holding the old one is logged out — which is the point,
  since changing a password is what you do when you think it leaked. `204`.

Future: `/api/v1/auth/microsoft/start` and `/callback`, added without changing the endpoints above.

## 5. Endpoint catalogue

Access column: **A** = `ADMIN` only, **A/E** = admin plus employees within their scope.

Scope means two different things depending on the resource, and both are enforced server-side:

- **Case-scoped endpoints** require an active assignment. An employee without one receives `404`, so the
  response does not confirm the case exists (ADR-0021).
- **Person endpoints** use the person-access predicate (ADR-0027): the directory is searchable by any
  authenticated user but returns `PersonSummary`, while `PersonDetail` and `PATCH` require the person to
  participate in a case currently assigned to the employee. Because search already discloses existence,
  a denied write returns `403`, not `404`.

### Users — `A` unless noted. **Implemented.**

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/api/v1/users` | Paginated; filters `query` (name or address, case-insensitive), `role`, `is_active` |
| `POST` | `/api/v1/users` | `201`. Creates a staff account; returns the one-time temporary password exactly once and never again (ADR-0026) |
| `GET` | `/api/v1/users/{user_id}` | |
| `PATCH` | `/api/v1/users/{user_id}` | `full_name`, `role`, `deactivated` — nothing else is accepted |
| `POST` | `/api/v1/users/{user_id}/password-reset` | Issues a new temporary password and revokes the user's sessions (ADR-0026) |
| `GET` | `/api/v1/users/directory` | **A/E** — `{id, full_name, role}` only, for assignee pickers and labels |

- The user DTO is `{id, email, full_name, role, must_change_password, is_active, deactivated_at,
  last_login_at, created_at, updated_at}`. Absent on purpose: the identity row and its `secret_hash`,
  every session, `created_by`, and the `failed_attempt_count`/`locked_until` counters. A test asserts
  the exact field set, and another asserts none of those names appears in any response or in the
  OpenAPI document's schema properties.
- **Creation** may create an `ADMIN` as well as an `EMPLOYEE`: with no self-service reset, a firm with
  one administrator has no way back from a lockout, and keeping a second admin is the documented
  mitigation. The new account always starts with `must_change_password = true`. A duplicate address is
  `409 USER_EMAIL_CONFLICT`, decided by the read *and* by the unique index — two concurrent creations
  both pass the read and one loses at the constraint.
- Unlike login, a malformed address here is a plain `422`: the caller is an authenticated admin, so
  there is no enumeration oracle to protect.
- **`PATCH`** is an allowlist, not a partial model of the row: `email`, `must_change_password`,
  `created_by` and every timestamp are rejected outright rather than silently ignored, because the
  request models forbid unknown fields. Omitted fields are left alone. Deactivating revokes every
  session of the target in the same transaction; reactivating restores login but does **not** restore
  the old sessions. Users are never hard-deleted, so historical audit rows keep resolving.
- **`password-reset`** is the whole account-recovery story in Release 1. It replaces the hash, sets
  `must_change_password`, clears any lockout, revokes every session the user has — including the one
  they may be using at that moment — and returns the new temporary password once.
- **The directory** is unpaginated and returns only active accounts: it is the internal staff list of
  a single consultancy, read to populate a dropdown, and paging it would make every caller reassemble
  it. It carries no email addresses. This is *not* the people directory — clients, lawyers and other
  external parties are `people`, not users.

### Operational

| Method | Path | Access | Notes |
| --- | --- | --- | --- |
| `GET` | `/healthz` | public | Liveness; touches nothing. **Implemented.** Unversioned on purpose — this is the infrastructure probe, and it is excluded from the OpenAPI document |
| `GET` | `/api/v1/healthz` | public | The same handler, published in the contract, and the path the browser uses through the same-origin proxy. **Implemented** |
| `GET` | `/readyz` | public | Database reachability (`SELECT 1`); no detail in the body. **Implemented.** Unversioned, excluded from the OpenAPI document |
| `GET` | `/api/v1/readyz` | public | The same handler, published in the contract. **Implemented** |

Health responses are `{"status": "ok"}`, readiness responses `{"status": "ready"}`, and neither
carries a version, an environment name or any dependency detail. A failing readiness check returns
`503` with the standard error envelope and the code `SERVICE_UNAVAILABLE`; the hostname, credentials,
driver message and topology stay in the server log, where the `request_id` in the body leads.

The split matters operationally: `/healthz` must keep succeeding while the database is down, or an
orchestrator will restart perfectly healthy containers during a database incident and turn an outage
into a longer one. `/readyz` is what takes an instance out of rotation. Storage reachability joins
`/readyz` in Phase 6, when the application first depends on it.

## 6. Frontend contract generation

FastAPI publishes the OpenAPI document; `openapi-typescript` generates
`apps/web/src/lib/api/schema.d.ts`, which is committed. CI regenerates it and fails on any diff, so
the client and server cannot drift silently and the web app needs no hand-written response types
(ADR-0017). The typed fetch wrapper attaches credentials and the CSRF header, and converts an error
envelope into a typed `ApiError` carrying `code`, which the Hebrew message mapper consumes.
